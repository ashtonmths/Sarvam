## What gets crawled

**Structure, never payloads.** Tables, views, columns, types, foreign keys, and
the dependencies inside view definitions.

The crawler reads `information_schema` and `pg_catalog`. It issues no `SELECT`
against your own tables, and a crawl of a hundred-million-row table produces the
same amount of stored data as a crawl of an empty one.

## The role to create

```sql
CREATE ROLE sadhak_reader LOGIN PASSWORD 'a-strong-password';
GRANT CONNECT ON DATABASE your_db TO sadhak_reader;
GRANT USAGE ON SCHEMA public TO sadhak_reader;
```

That is the whole grant. There is deliberately no `GRANT SELECT ON ALL TABLES`:
every query the crawler runs reads `information_schema` or `pg_catalog`, which
Postgres exposes to any role that can connect, so a table `SELECT` would grant
access the crawler never uses.

This page previously published a blanket `SELECT ON ALL TABLES IN SCHEMA public`.
That was wrong, and wrong in the expensive direction — it asked customers to hand
over read access to every row in their database to run a crawl that only reads
structure. The role above is the one the code actually needs, and a unit test
asserts the published grant never contains a table `SELECT` so the two cannot
drift again.

The session is also hardened read-only on connect, so a write through this
connection is a database error rather than something a code review has to catch.

## Read and revert are separate

The role above is read-only and that is the only credential Sadhak needs. Reverts
in Postgres are **proposed as SQL for a human to run** rather than executed, so
there is no write credential for this connector at all.

## Known limits

- Dynamic SQL built at runtime is invisible to a structural crawl. Those edges
  come from the [Historian](/docs/mcp) reading discussion, and arrive as
  `llm_inferred` — which warns and never blocks.
- Cross-database references are not followed. Connect each database separately.
